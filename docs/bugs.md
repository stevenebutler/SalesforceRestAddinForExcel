9. **`in` / `on` criteria operators are incomplete / misleading vs legacy.** Legacy only special-cased `in`/`on` on **reference (lookup) fields**: value cell = Excel range address or named range → collect 15/18-char Ids → join-style queries (intended one SOQL per Id; `on` set a flag that was unused so `in`≈`on`). Non-reference `in` fell through and produced invalid SOQL-ish clauses. Our port: reference + `in` builds `Field IN ('id',…)` from a **comma-separated Id list** (not an Excel range); non-reference `in` still has no real `IN (...)` support. Wizard offers `in` for all fields. See FR-QTD-4. **Open question — what exactly to do?** Options include: (a) port legacy range join (`build_ref_range`) for reference `in`/`on`, with batched `IN (...)` as the improvement; (b) keep Id-list `IN (...)` for lookups and document it; (c) also support true multi-value `IN` / OR for non-reference fields; (d) hide or disable `in`/`on` in the wizard except on lookup fields until decided. Do not implement until product choice is clear.
